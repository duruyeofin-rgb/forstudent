# 04. 기술 구성과 데이터 구조

**기록 저장, 교사 대시보드, 개발 방식, 배포**는 각각 결정합니다. GitHub·Supabase·Vercel 가입은 기본 조건이 아닙니다.

## 1. 기록과 대시보드를 독립적으로 선택

| 학생별 기록 | 교사 대시보드 | 권장 |
|---|---|---|
| 아니오 (기본) | 아니오 (기본) | 정적 HTML·CSS·JavaScript; DB·로그인·교사 화면 없음 |
| 아니오 | 예 | 어떤 교사 기능이 필요한지 다시 질문. 개인별 성장 대시보드는 데이터 없이 만들 수 없음 |
| 예 | 아니오 | 인증·권한이 검증된 서버+DB. 필요한 경우 보호된 열람/내보내기만 제공 |
| 예 | 예 | 인증·권한이 검증된 서버+DB + 선택형 교사 화면 (`06-teacher-dashboard.md`) |

기록이 불필요하면 DB를 만들지 않습니다. 학생별 기록은 대시보드가 없어도 보호해야 합니다. 기록과 대시보드 필요 여부를 질문하고 확인받되, **기본값은 둘 다 만들지 않음**입니다.

## 2. 개발과 배포 환경은 선택

- **정적 앱**: `index.html` 또는 소규모 HTML·CSS·JavaScript로 시작합니다. GitHub·DB 없이 로컬 미리보기에서 실행할 수 있습니다. 공개 배포는 별도로 선택합니다.
- **Google Apps Script**: 구글 계정으로 단순 웹앱을 배포합니다. `Code.gs`의 `doGet()` + `Index.html`(HTML Service)로 구성합니다. **React/Vite 프로젝트를 그대로 붙여넣지 않습니다.** 학교 계정의 관리자 제한, 실행 계정, 접근 범위를 확인합니다. `09-simple-deployment.md` 참고.
- **서버 기록형 권장 사례**: 화면 React + Vite + TypeScript + Tailwind CSS / DB와 인증 Supabase / 배포 Vercel. **운영 경험에 따른 예시이지 필수 연동이 아닙니다.** 다른 구성이어도 서버 측 권한·삭제·복구 정책을 지킵니다.
- **GitHub**: 버전 관리·협업이나 특정 클라우드 개발 환경에서 필요할 때에만 연결합니다.
- **소리**: 필요하면 브라우저 `speechSynthesis`를 사용합니다. 기기마다 다른 음성 인식 결과로 학생을 단정하지 않습니다.

## 기록형 앱의 폴더 구조 예시 (정적 앱에는 강요하지 않음)

```
src/student/    학생 화면
src/teacher/    교사 화면 (대시보드 선택 시)
src/lib/        서버·계산·오프라인 저장
src/data/       교육 내용
scripts/        필요한 점검
supabase/       Supabase 사용 시 SQL
docs/           기획서·검수
```

## 학생 입장 (서버 기록형 Supabase 구성 예시)

- 학급 코드(숫자 6자리) + 번호 입력은 기존 운영 사례입니다. 대시보드를 선택했을 때만 QR·코드 교사 화면을 둡니다. **학급 코드·번호는 본인 인증이 아닙니다.** 타 학생 번호로 재입장해 기록을 열람·수정할 수 없는지 서버에서 검증하고 안전한 사용자 검증을 추가합니다. 이를 보장하지 못하면 학생별 기록을 배포하지 않습니다.
- 서버는 입장 시 익명 로그인(Supabase *Anonymous sign-ins*를 대시보드에서 켜야 합니다)을 만들고, 서버 함수(`join_class(코드, 번호)`)가 학생 행을 만들거나 찾아 그 익명 사용자와 묶습니다.
- **공용 태블릿이면 항상 학급 코드부터** 시작합니다. 저장된 학생으로 자동 입장하면 이전 학생의 기록이 열리는 사고가 납니다. QR, 일반 주소, 새로고침, 브라우저 뒤로 가기 복원 모두 빈 코드 입력 화면에서 시작하게 합니다. (학생 한 명이 기기 한 대를 전용으로 쓰는 환경이면 선생님과 정해서 자동 입장을 허용할 수 있습니다.)
- 번호 선택 화면에는 입력한 학급 코드를 보여 줍니다.

## 교사 로그인 (필요할 때만)

- 교사는 **아이디(별명) + 비밀번호**로 가입·로그인합니다. 이메일을 받지 않기 위해 내부적으로 `아이디@teacher.<앱이름>.invalid` 같은 가짜 이메일로 바꿔 인증 서비스에 넣습니다. 같은 아이디가 있으면 "이미 쓰는 아이디"라고 안내합니다.
- 단점: 이메일이 없어서 **비밀번호를 잊으면 복구할 수 없습니다.** 가입 화면과 README에 분명히 적습니다.
- 아무나 학급을 만들지 못하게 하려면 **초대 암호**(해시만 DB에 보관)를 통과한 계정만 교사로 등록합니다.

## 데이터 구조 (Supabase 기록형 선택 시)

`templates/schema-starter.sql`에 시작점이 있습니다. 이름은 프로젝트에 맞게 바꾸세요.

| 표 | 내용 |
|---|---|
| `classes` | 학급 이름, 코드, 인원 수, 교사 |
| `students` | 학급, **번호**, 익명 사용자 연결, 진행 상태(선택한 캐릭터·보상 등) |
| `progress` | 학생·단원·단계별 통과 여부, 첫 시도 맞힘 수 |
| `attempts` | **문항 하나하나의 결과**: 학생, 단원, 문항 번호, 고른 답, 정오, **첫 시도 여부**, 피드백, 시각 |
| `teacher_notes` | 필요한 경우에만 저장하는 교사 피드백 메모 (학생은 못 봄) |
| 활동별 표 | 미션·복습·이해 활동처럼 모양이 다른 활동은 **별도 표**로 둡니다 (정답률을 왜곡하지 않기 위해) |

설계 원칙:
- 성장 분석은 `attempts`에서 **계산만** 합니다. 계산 결과를 따로 저장하지 않으면 기준을 바꿔도 과거 기록을 다시 계산할 수 있습니다.
- 문항 번호는 교육 내용 파일의 순서에서 만들어지므로, 수업이 시작된 뒤에는 순서를 바꾸지 않습니다.
- 표가 아직 없어도 앱이 멈추지 않게 합니다. (새 기능의 표가 준비되기 전에는 그 기능만 건너뜁니다. "표 없음" 오류 코드를 알아보고 조용히 처리합니다.)
- 모든 SQL은 여러 번 실행해도 안전하게(`if not exists`, `drop policy if exists`) 쓰고, 파일 머리에 **적용 순서와 되돌리기 SQL**을 적습니다.

## 기록형에서 오프라인에도 기록이 사라지지 않게

교실 와이파이는 끊깁니다. 저장은 **기기에 먼저 보관 → 서버로 전송** 순서로 합니다.

1. 기록(`attempt`, `progress`, 학생 상태 변경)을 기기 저장소의 대기열에 넣는다.
2. 대기열을 순서대로 보낸다. **네트워크 오류**(서버 오류 코드가 없는 실패)면 멈추고 남겨 둔다. **권한·형식 오류**(오류 코드가 있음)면 버리고 로그만 남긴다.
3. 입장할 때, 인터넷이 다시 연결될 때, 15초마다 다시 보낸다.
4. 같은 학생의 상태 변경은 하나로 합치고, 같은 키의 진도 기록은 마지막 값만 남긴다.
5. 서버에서 같은 ID의 재전송은 **한 번만 반영**(멱등)되게 한다.
6. 보내는 중인 전송을 기다린 뒤 다음 전송을 시작해서, 전송 중인 행을 덮어쓰지 않게 한다.
7. 기기 저장 공간과 서버가 모두 실패했다면 거짓으로 "저장됨"이라고 하지 않는다.

저장 직후에는 성공 화면을 따로 보이지 않고 **바로 다음 화면**으로 넘어갑니다 (저학년은 성공 화면에서 멈춥니다).

## 기록형에서 교사가 초기화했을 때 학생 기기가 따라가게

학생 기기에는 예전 값이 남아 있어서, 그냥 두면 다음 저장 때 교사가 초기화한 값을 덮어씁니다.

- 학생 기기가 **20초마다, 그리고 화면이 다시 보일 때** 자기 기록을 서버에서 읽어 기기 값과 비교합니다.
- 보낼 기록이 없고 마지막 변경이 몇 초 지난 안전한 때만 비교합니다.
- 달라졌으면 서버 값으로 맞추고 처음 화면(선택 화면)으로 돌아갑니다.
- 더 엄격하게는 초기화마다 **세대 값(epoch)**을 바꾸고, 서버가 오래된 세대의 재전송을 거부하게 합니다.

## 환경 변수와 배포 (해당 구성에서만)

- **정적 앱**: 서버·DB·환경 변수는 만들지 않습니다. 공개 배포가 필요한 경우에만 호스팅을 고릅니다.
- **Apps Script**: `Code.gs`, `Index.html`에 맞춰 작성하고 실행 사용자·접근 대상을 확인합니다. 서버의 비밀값을 HTML에 내보내지 않습니다.
- **Supabase 구성**: `VITE_SUPABASE_URL`과 `VITE_SUPABASE_ANON_KEY` 같은 공개 가능한 연결 설정만 클라이언트에 둡니다. 서비스 역할 키는 브라우저·Git·채팅·로그에 남기지 않습니다.
- **Vercel 등 배포 서비스 선택 시**: 올바른 프로젝트·공개 주소를 대조하고 배포 승인을 받은 뒤 실행합니다. Git 자동 연동은 필수 아닙니다.
- 무료 요금제·휴면 정책·배포 권한은 변할 수 있으므로 실제 사용 시 확인합니다. 기록형은 복구·삭제 절차도 문서화합니다.
