# 08. 실제 프로젝트에서 배운 것

초등 1학년 한글 받침 학습 웹앱을 만들며 겪은 일들입니다. 같은 실수를 되풀이하지 않도록 **무슨 일이 있었고, 그래서 어떻게 하는지**를 적었습니다. (학생 정보나 비밀값은 포함하지 않았습니다.)

## 목적과 설계

1. **목적을 먼저 한 문장으로 선언했습니다.** "학생의 성장을 기록하고, 교사가 그것으로 피드백한다." 게임 요소를 넣을 때마다 이 목적을 해치는지 물었고, 해치는 것은 줄였습니다. → 기획 때 목적 문장을 만들고 지침 파일 맨 위에 둡니다.
2. **기능을 늘리기 전에 하나를 끝까지** 만들었습니다. 한 번에 많은 활동을 만들면 어느 것도 안정적이지 않습니다. → 첫 버전은 기능 하나.
3. **교사가 10~20초 안에 누구를 먼저 도울지 알 수 있게** 하는 것을 성공 기준으로 삼았습니다. 그래프를 늘리는 것보다 "먼저 살펴볼 학생" 목록이 더 쓸모 있었습니다.
4. 활동이 한 가지 모양(듣고 고르기만)이면 2~3주째에 질린다는 지적이 있었습니다. → 활동 모양을 섞는 계획을 처음부터 세웁니다 (소리 분류, 글자 타일, 따라 말하기 같은 가벼운 활동).

## 기록과 분석

5. **첫 시도와 재시도를 구분**해서 저장한 것이 성장 분석의 바탕이 되었습니다. 나중에 넣기 어려운 정보라서 처음부터 저장합니다.
6. 한 번의 학습 안에서 문제 순서가 "성장"처럼 보이는 오류가 있었습니다(앞 절반 50% → 뒤 절반 75%). → 초기/최근은 문제 개수가 아니라 **학습 회차**로 나눕니다.
7. "반복 오류"를 처음에는 한 번이라도 틀린 것으로 잡았다가, **나중에 맞힌 낱말까지 포함하는 문제**가 있었습니다. → 서로 다른 회차에서 틀리고 **가장 최근에도** 틀리는 것만.
8. **놀이 활동(미션)의 결과를 정답률에 섞지 않았습니다.** 섞으면 성장 추세가 왜곡됩니다. 별도 표에 저장하고 교사 화면에서 따로 봅니다.
9. 음성 인식은 학생이 틀리게 읽어도 **자주 쓰는 문장으로 알아서 고쳐 적는** 경우가 있었습니다. 처음에는 후보 중 정답에 가장 가까운 것을 골라서 잘못 읽어도 통과했습니다. → 틀린 어절이 하나도 없어야 통과, 인식 1순위만 사용, 인식된 글자를 교사에게 보여 주고, 3번 실패하면 **선생님 확인**.

## 화면과 한국어

10. 꿈 완성 화면에 "멋진 의사이(가) 되었어요!"가 그대로 나왔습니다. → 조사 함수를 만들고, 소스에서 "이(가)" 같은 표기를 찾는 **점검 스크립트**를 추가했습니다.
11. 공용 태블릿에서 QR을 찍었는데 **이전 학생의 기록이 열렸습니다.** → QR·일반 주소·새로고침·복원 모두 학급 코드부터 시작하고, 자동 입장을 없앴습니다.
12. AI가 만든 그림에 **원하지 않은 글자**("WEBTOON")가 들어가거나 스타일이 어긋난 장면이 있었습니다. → 글자는 그림에 넣지 않고, 어긋난 그림은 다시 만들고, 확인용 모음 이미지로 한눈에 점검합니다.
13. 선생님이 "할 수 있어?"라고 물었을 때 바로 만들지 않고 가능 여부를 설명했고, 선생님이 "만들지 마"라고 하면 만들지 않았습니다. → 질문과 요청을 구분합니다.

## 저장과 초기화

14. 교사가 초기화했는데 **학생 태블릿에 남은 예전 별 수**가 나중에 저장되면서 초기화가 무효가 되는 문제가 있었습니다. → 기기가 서버 값과 주기적으로 비교해 따라가게 했습니다.
15. 초기화가 attempts만 지우고 진도·별·꿈 이야기를 남기는 **불완전 초기화**였습니다. → 지울 것을 고르는 창, 학급 전체는 낱말 입력, 학생 줄에서 개별 초기화.
16. 새 기능의 DB 표를 운영에 적용하기 전에 앱이 먼저 배포돼도 **앱이 멈추지 않게** 했습니다("표 없음" 오류를 알아보고 해당 기능만 건너뜀). 운영 DB 변경은 선생님이 SQL 편집기에서 직접 실행했습니다.
17. 백업 파일 내려받기 기능을 만들었다가, 선생님이 "필요 없다"고 해서 뺐습니다. 백업을 두면 학생 기록 파일이 선생님 PC에 남는다는 점을 먼저 설명해 두면 결정이 쉽습니다.

## 작업 방식과 비용

18. **다른 도구(또는 사람)가 같은 저장소를 동시에 고치고 있었습니다.** 원격 저장소를 확인하지 않고 만든 맞춤 미션 기능이, 이미 합쳐져 운영에 올라간 다른 구현과 **같은 파일 이름·같은 DB 표 이름**으로 충돌했습니다. → 시작 전에 `git fetch`로 원격의 최근 커밋과 브랜치를 보고, 같은 기능이 이미 있는지 확인합니다. 선생님이 다른 도구도 쓰는지 한 번 묻습니다.
19. 확인용 서버를 띄웠는데 **연결 값(환경 변수)이 없어서** "연결 값이 설정되지 않았어요" 안내가 떴습니다. → 확인용 주소를 알려 주기 전에 직접 열어 보고, 실제 학급이 아니라 시험용 학급으로 들어가라고 안내합니다.
20. **이미지 생성 비용**이 예상보다 많이 나와 선생님이 걱정했습니다. → 유료 호출 전에 장수와 비용을 알리고, 소량 시험, 끝나면 키 폐기 안내.
21. 문서가 코드보다 늦어져 README에 **옛 동작**(자동 입장, "네 문항" 등)이 남았습니다. → 동작을 바꾸는 변경에는 문서 수정을 같은 작업에 넣습니다.
22. 인증이 한 번 일시적으로 실패한 배포가 두 번째에 성공했습니다. → 배포 실패는 원인을 확인하고 한 번 다시 시도하되, 계정·프로젝트가 맞는지 확인합니다.
23. 선생님이 지시서를 길게 써서 주었을 때(기능 목록, 안전 수칙, 보고 형식) **그 구조를 그대로 따라** 단계별로 진행하고 마지막에 같은 형식으로 보고했습니다. → 선생님이 만든 순서와 보고 형식이 있으면 우선합니다.
