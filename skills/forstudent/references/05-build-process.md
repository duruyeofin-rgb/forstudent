# 05. 만드는 순서와 안전 수칙

선생님의 기획이 정리된 뒤(0~2단계)부터 실제로 만들고 올리는 과정입니다. 순서를 지키는 이유는 **되돌릴 수 없는 일을 마지막에, 확인된 뒤에** 하기 위해서입니다.

## 0. 시작하기 전에

- 현재 작업 상태와 Git 브랜치를 확인하고, **원격 저장소의 최신 내용을 먼저 가져와 봅니다**(`git fetch`와 최근 커밋 확인). 같은 저장소를 다른 사람이나 다른 도구가 고쳤을 수 있습니다.
- 작업 브랜치를 따로 만들어 개발합니다. 다른 미완료 작업을 덮어쓰지 않습니다.
- 프로젝트 지침 파일(`CLAUDE.md` 또는 `AGENTS.md`, 양식: `templates/project-instructions.md`)에 저장소 주소, DB 프로젝트 ID, 배포 프로젝트 ID, 지켜야 할 규칙을 적습니다. 여러 프로젝트를 다루면 ID를 헷갈려 엉뚱한 곳을 바꾸게 됩니다.

## 1. 분석 (기존 코드가 있을 때)

- 관련 파일을 먼저 읽고 **재사용할 것 / 새로 필요한 것**을 나눕니다.
- 불필요한 재작성과 대규모 리팩터링을 하지 않습니다. 선생님이 요청하지 않은 화면은 다시 디자인하지 않습니다.
- 기존 학습 기능, 보상, 통과 기준, 저장된 기록(문항 번호)을 보존합니다.

## 2. 계획과 위험 요소

간결하게 보여 주고 시작합니다.
- 무엇을 만들고, 어디를 고치는가
- 위험: 유료 서비스, 운영 DB 변경, 되돌릴 수 없는 삭제, 배포, 기존 기능 영향, 필요한 그림·자료
- 승인이 필요한 것 (아래 "승인이 필요한 일")

## 3. 단계별 개발

| 단계 | 내용 | 끝났다는 기준 |
|---|---|---|
| 1차 기반 | 타입·데이터 구조, **핵심 계산**(점수·통과·상태·추천), 내용 점검 스크립트, 개인정보 점검, 기록 저장 구조 | 점검 스크립트 통과 (화면이 없어도 계산이 맞음) |
| 2차 첫 기능 | 가장 원한 기능 **하나**를 시작 화면부터 완료·기록 저장·교사 화면 표시까지 | 실제로 눌러 보며 동작 확인 |
| 3차 나머지 | 2차의 공통 구조를 재사용해 추가. 중복 코드를 늘리지 않음 | 기능별 동작 확인 |
| 4차 통합 | 상황별 점검(아래), 기존 기능 회귀, 문서 갱신 | 점검표 통과 + 보고 |

기능 개수를 늘리는 것보다 **첫 기능이 안정적으로 동작하는 것**이 우선입니다.

공통 컴포넌트로 만들고 기능마다 **연출만** 바꾸면, 새 기능을 추가해도 문제 화면·기록 저장·접근성 처리를 다시 만들지 않습니다 (예: 장면 컴포넌트만 바뀌고 문제 풀이 화면은 모든 게임이 같음).

## 4. 검증

**항상 실행하고 결과를 보여 줍니다.** 실행하지 못했다면 통과로 쓰지 않습니다.

1. **타입 검사와 빌드**
2. **점검 스크립트** (프로젝트의 `scripts/check` 같은 곳): 내용 데이터(문항·낱말·정답·발음·뜻), 한국어 조사, 핵심 계산, 개인정보 점검
3. **가짜 서버로 화면 확인**: 운영 DB에 연결하지 않고, 서버 응답을 가짜로 만든 임시 확인 환경에서 학생 화면을 **실제로 눌러 봅니다**. 어떤 요청이 나갔는지(어느 표에, 어떤 값으로) 기록해서 "다른 학생까지 건드리지 않았다", "정답률에 섞이지 않았다"를 확인합니다. 확인용 임시 파일은 끝나면 지웁니다.
4. **상황별 점검** (해당하는 것):
   - 학습 기록이 없는 학생 / 오류가 한 번뿐인 학생 / 같은 항목을 여러 번 틀리는 학생
   - 낱말은 잘하지만 문장에서 약한 학생
   - 이미 한 활동을 다시 여는 학생 (중복 지급·중복 출제 없음)
   - 활동 도중 페이지를 닫은 학생 (이어하기 또는 다시 시작이 꼬이지 않음)
   - 인터넷이 불안정한 상황, DB 표가 아직 없는 상황
   - 교사가 기록을 초기화한 상황
   - 새로고침, 뒤로 가기, 같은 단추 연타
   - 기존 별·보상·진도 계산이 바뀌지 않았는지
5. **작업 중에 확인한 것이 거짓 성공이 되지 않게**: 임시 화면(시연용)과 실제 동작을 구분하고, 확인하지 못한 것은 그대로 적습니다.
6. **실제 기기**(학생이 쓰는 태블릿)에서의 확인은 선생님이 합니다. 확인 방법(주소, 순서, 볼 것)을 적어 드립니다. 확인용 주소를 PC에서 띄울 때는 같은 와이파이가 필요하고, 실제 학급이 아닌 **시험용 학급**으로 들어가라고 안내합니다 (풀이 기록과 별이 진짜 학생에게 쌓이지 않도록).

## 5. 승인이 필요한 일 (먼저 설명하고 확인)

- **유료 사용**: 이미지 생성 같은 유료 API. 예상 장수·비용을 말하고, 소량으로 시험한 뒤 늘립니다. 끝나면 키를 폐기하도록 안내합니다.
- **되돌릴 수 없는 일**: 삭제, 초기화, 강제 푸시, 작업 폴더 밖의 대량 삭제
- **운영 DB 변경**: 스키마·정책·데이터. 먼저 SQL 파일로 쓰고, **되돌리기 SQL**과 백업을 만들고, 선생님이 승인한 뒤에 실행합니다. 선생님이 직접 SQL 편집기에서 실행하기를 원하면 그 방식을 따르고, 승인이 거절된 작업을 다른 방법으로 우회하지 않습니다.
- **배포**: 선생님이 "배포까지"를 맡긴 경우에도 운영 사이트에 올리기 전에 무엇이 바뀌는지 알립니다. 승인 없이 올리지 말라는 지시가 있으면 따릅니다.
- 선생님이 막은 동작(거절한 승인, 사용자가 둔 금지 규칙)을 지우거나 우회하지 않습니다.

## 6. DB 변경 절차

1. SQL 파일을 작성한다 (여러 번 실행해도 안전, 적용 순서, 되돌리기 SQL 포함).
2. 표가 없어도 앱이 동작하는지 확인한다.
3. 운영 DB 적용 전: 영향 범위와 되돌리는 방법을 알리고 승인받는다. 기존 데이터를 바꾸는 경우 백업을 남긴다.
4. 적용 후: 새 표에서 **비로그인·본인·타인** 접근을 실제로 시험한다 (`03-privacy-and-safety.md`).
5. 프로젝트 지침 파일에 적용한 SQL과 날짜를 기록한다.

## 7. 배포 순서

1. 현재 프로젝트에 연결된 배포 프로젝트의 ID가 지침 파일의 값과 같은지 **대조**한다 (다른 프로젝트를 건드리지 않기 위해).
2. 의도한 변경만 비밀값 검사 후 커밋·푸시한다. 남은 변경과 보내지 않은 커밋이 없는지 확인한다.
3. 배포한다. 배포 상태가 **준비됨(Ready)**인지와 실제 공개 주소를 확인한다. 한 번 실패하면 원인을 확인하고 다시 시도한다(일시적인 인증 오류가 있을 수 있음).
4. 공개 주소에서 **응답 200, 핵심 화면 동작, 브라우저 콘솔 오류 없음, 서버 로그**를 확인한다. DB가 있으면 새로 배포된 서버에서도 **읽기와 쓰기**가 이어지는지 확인한다.
5. 기관이 정한 점검 도구가 있으면 배포 뒤 한 번 실행한다. 결과를 쉬운 말로 알리고, **위험**으로 나온 항목만 고쳐서 다시 배포한다. 권고·미확인 항목은 참고로 알린다 (점검이 배포를 막거나 되돌리게 하지 않고, 점검 통과가 보안 보증이라는 뜻도 아니다).
6. 결과와 공개 주소를 보고한다.

## 8. 오류가 나면

- 추측하지 않고 **실제 로그·계정·실행 환경·권한 설정**으로 원인을 찾는다.
- 고친 뒤 같은 검사를 다시 한다.
- 선생님에게는 원인을 쉬운 말로 설명하고, 내 실수였으면 그대로 말한다.

## 9. 보고

작업이 끝나면 `templates/final-report.md` 형식으로 보고합니다. 길어도 **확인한 것과 확인하지 못한 것**은 반드시 나눕니다.

## 10. 소통

- 선생님이 쓰는 말로 말합니다. 개발 용어는 한 번 풀어 줍니다.
- 작업이 길어지면 지금 무엇을 하는지 한두 문장으로 알립니다.
- "할 수 있어?"는 보통 질문입니다. 가능 여부와 장단점을 답하고, 만들지는 선생님이 정합니다.
- 선생님이 "만들지 마"라고 하면 만들지 않고, 그 결정을 따릅니다.
- 선생님이 비용을 걱정하면 불필요한 유료 호출·명령을 하지 않습니다.
