# forstudent — 선생님이 학생을 위한 웹앱을 만드는 방법

이 스킬은 한 초등학교 선생님이 학습 웹앱을 처음부터 만들며 얻은 방식을 다른 교실에서도 쓰도록 정리한 것입니다. 중심 생각은 세 가지입니다.

1. **기능이 아니라 '배움이 멈추는 순간'에서 시작합니다.** 웹앱은 그 순간을 풀기 위한 도구입니다. 기능 목록부터 만들면 화려하지만 교실에서 안 쓰이는 앱이 됩니다.
2. **기록 저장과 교사 대시보드는 독립적인 선택 사항입니다.** 기록 없는 학습 도구도 가치가 있습니다. 필요할 때만 기록을 모아 교사의 피드백에 활용하고, 앱이 학생을 평가하지 않습니다.
3. **학생 정보는 가장 적게 받습니다.** 받지 않은 정보는 새어 나갈 수 없습니다.

선생님은 개발자가 아닐 수 있습니다. 쉬운 우리말로 말하고, 용어는 한 번 풀어 주고, 작업이 길어지면 지금 무엇을 하는지 한두 문장으로 알려 주세요.

## 0단계 — 먼저 묻습니다 (코드와 계획보다 먼저)

스킬이 시작되면 아래 네 질문을 **그대로** 한 번에 보여 주고 답을 기다립니다. 답을 받기 전에는 설계·코드·저장소·DB를 만들지 않습니다. 교실을 가장 잘 아는 사람은 선생님이고, 질문을 건너뛰면 그럴듯하지만 교실에 맞지 않는 앱이 되기 때문입니다.

> 1. 학생의 배움이 멈추는 순간은 언제입니까?
> 2. 학생이 가장 먼저 해야 할 일은 무엇입니까?
> 3. 웹앱 또는 도구로써 구현하고 싶은 기능은 무엇입니까?
> 4. 웹앱에 들어가서는 안되는 정보는 무엇입니까?

질문 아래에 이 한 줄만 덧붙입니다: "한두 문장이면 충분해요. 막막하면 '예시 보여 줘'라고 말씀해 주세요."

- 네 질문을 쪼개서 여러 번에 걸쳐 묻지 않습니다. 선생님이 한 번에 생각을 정리할 수 있게 같이 보여 줍니다.
- "예시 보여 줘"라고 하면 `references/01-interview.md`에서 비슷한 교과의 예시를 보여 줍니다.
- 선생님이 이미 대화에서 답을 길게 설명했다면 다시 묻지 말고, 답을 추려서 "이렇게 이해했는데 맞나요?"로 확인만 합니다.
- 답이 모호하면 되묻기는 **최대 두 번**, 정말 모호한 질문에만 합니다 (후속 질문 목록은 `01-interview.md`).
- 4번이 비어 있거나 "없다"여도 넘어가지 않습니다. 기본 금지 목록(`03-privacy-and-safety.md`)을 제안하고 확인받습니다. 선생님이 떠올리지 못한 정보가 가장 위험하기 때문입니다.

## 1단계 — 답을 설계로 바꿉니다

| 질문 | 설계에 쓰는 방법 |
|---|---|
| 1. 배움이 멈추는 순간 | 이 순간을 **감지할 기록**(첫 시도 결과, 반복해서 틀린 항목, 도움 요청, 며칠째 접속 없음)을 정하고, 학생 화면에 **힌트→다시 해 보기→선생님 도움** 흐름을 만듭니다. 교사 화면의 "먼저 살펴볼 학생" 기준이 됩니다. |
| 2. 가장 먼저 할 일 | **첫 화면에는 한 가지 일만** 둡니다. 입장은 로그인 없이 학급 코드와 번호로, 10초 안에 첫 활동을 시작하게 합니다. |
| 3. 구현하고 싶은 기능 | 필수 / 있으면 좋음 / 나중에로 나누고, **첫 버전은 하나를 끝까지** 완성합니다. 기능이 학습 기록과 교사 확인에 어떻게 이어지는지 한 줄씩 적게 합니다. |
| 4. 들어가면 안 되는 정보 | **저장하지 않을 항목 목록**을 만들어 데이터 구조·화면·내보내기 파일에서 모두 뺍니다. 코드 점검(`templates/privacy-check.mjs`)으로 되돌아오지 않게 지킵니다. |

그리고 **두 가지를 따로 확인합니다.** (가) 학생별 학습 기록을 서버에 지속적으로 저장해야 하는가? (나) 교사 대시보드가 필요한가? **기본값은 둘 다 아니오**입니다. 기록이 없다면 DB·학생 로그인·대시보드를 만들지 않습니다. 기록은 필요하지만 대시보드는 불필요하다면 안전한 저장과 필요한 경우 보호된 내보내기만 설계합니다. 학생별 기록을 저장할 경우 대시보드 유무와 관계없이 인증·접근 통제가 필수입니다. `references/04-architecture.md` 참고.

## 2단계 — 만들기 전에 정리해서 보여 줍니다

1. 답을 **5줄 기획 요약**으로 정리해 선생님께 확인받습니다 (양식: `templates/project-brief.md`). 확인된 내용은 프로젝트 안 `docs/기획서.md`로 저장합니다.
2. 기존 프로젝트가 있으면 관련 파일과 현재 변경 사항을 확인합니다. **Git 저장소가 있을 때만** 브랜치와 상태를 확인하며, 원격이 연결된 경우에만 원격 변경을 확인합니다. GitHub에 가입하거나 저장소를 새로 만들도록 강제하지 않습니다. 재사용할 것과 새로 필요한 것을 나누고 불필요한 재작성은 하지 않습니다.
3. **구현 계획과 위험 요소를 간결하게** 보여 주고 시작합니다. 유료 서비스, 되돌릴 수 없는 일, 운영 DB 변경, 배포가 필요하면 이 단계에서 미리 알리고 승인받습니다.

3. **개발·배포 환경을 별도 선택합니다.** 간단한 연습 앱은 HTML·CSS·JavaScript 정적 앱으로 만듭니다. GitHub 없는 배포가 필요하면 Google Apps Script(HTML Service)도 선택할 수 있습니다. 기록형 앱에는 인증·안전한 DB가 필요하며, Supabase·Vercel은 가능한 권장 조합일 뿐 필수가 아닙니다. 선생님이 원하지 않는 계정·연동·대시보드를 추가하지 않습니다. `references/09-simple-deployment.md` 참고.

## 3단계 — 단계별로 만듭니다

| 단계 | 하는 일 |
|---|---|
| 1차 기반 | 학습 내용·핵심 계산·개인정보 점검을 준비합니다. **기록형에서만** 데이터베이스·학생 인증·저장 구조를 만듭니다. |
| 2차 첫 기능 완성 | 선생님이 가장 원한 기능 **하나**를 처음부터 끝까지 만들고, 실제로 눌러 보며 동작을 확인합니다. |
| 3차 나머지 기능 | 2차에서 검증한 공통 구조를 재사용해 나머지를 만듭니다. 중복 코드를 늘리지 않습니다. |
| 4차 통합 검증 | 실제 기기·새로고침·기존 기능을 확인합니다. **기록형에서만** 저장·권한·초기화를 검증하고 **대시보드 선택 시에만** 교사 화면을 검증합니다. |

각 단계의 세부 방법은 `05-build-process.md`, 학생 화면 원칙은 `02-learning-design.md`, 교사 화면은 `06-teacher-dashboard.md`를 읽으세요. 미션 개수나 기능 수를 늘리는 것보다 **첫 기능이 안정적으로 동작하는 것**이 우선입니다.

## 4단계 — 검증하고 정직하게 보고합니다

- 선택한 구성에 맞는 빌드 또는 실행, 내용·개인정보 점검, 화면 동작 검사를 실시합니다. 서버·DB가 있는 앱에만 가짜 서버·DB 테스트를 적용합니다. 하지 않은 검사는 통과했다고 보고하지 않습니다.
- 마지막 보고는 `templates/final-report.md` 형식으로, **확인한 것과 확인하지 못한 것을 나눠** 씁니다. 완성된 그림처럼 보이는 시연 화면과 실제로 동작하는 기능을 구분합니다.
- 태블릿 같은 실제 기기에서 선생님이 확인하는 방법도 함께 적어 줍니다.

## 항상 지키는 원칙

- **목적이 먼저입니다.** 게임 요소가 학습 기록과 교사 피드백이라는 목적을 해치면 빼거나 줄입니다.
- **학생을 자동으로 평가하지 않습니다.** 사실과 패턴(예: 같은 낱말을 여러 날 틀림)을 보여 주고 판단은 선생님이 합니다. 음성 인식처럼 불확실한 결과는 능력으로 단정하지 않습니다.
- **저학년 화면에는 벌점·시간제한·순위가 없습니다.** 틀려도 힌트를 보고 다시 해 볼 수 있습니다.
- **비밀번호·토큰·API 키는 채팅·Git·로그에 두지 않습니다.** 공개용 키와 서버 비밀값을 구분합니다.
- **유료 사용, 되돌릴 수 없는 삭제·초기화, 운영 DB 변경, 배포는 먼저 설명하고 승인받습니다.** 운영 데이터를 바꾸기 전에는 되돌릴 방법을 남깁니다.
- **요청하지 않은 것은 만들지 않습니다.** "할 수 있어?"라는 질문에는 가능 여부와 장단점을 먼저 답하고, 만들기 전에 확인합니다.
- **GitHub·Supabase·Vercel과 교사 대시보드는 필수가 아닙니다.** 학생별 기록도 요청하지 않으면 만들지 않습니다. 단, 학생별 기록을 저장한다면 검증된 본인 확인·권한 분리를 생략하지 않습니다.
- **학교·기관의 정책을 우회하지 않습니다.** 막히면 멈추고 보고합니다.
- **문서도 코드와 함께 고칩니다.** 화면 동작이 바뀌면 README와 프로젝트 지침도 같이 맞춥니다.
